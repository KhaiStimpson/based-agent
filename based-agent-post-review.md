- Blocker: Evolution approval is not actually human-gated before promotion. The extension exposes `approve_evolution` as a normal tool (`based-agent/.pi/extensions/evolution-governor.ts:119`), and `lifecycleApprove` accepts any caller-provided/default `approved_by` then moves the proposal to `approved` (`based-agent/.pi/extensions/evolution-governor.ts:133-138`). Promotion only checks `status === "approved"` plus safety/regression/target/content gates; it does not require trusted human approval metadata or enforce `approval_required` (`based-agent/.pi/extensions/evolution-governor.ts:88-95`, `based-agent/.pi/extensions/evolution-governor.ts:147-151`). This violates the stated promotion safety requirement that broad/governed evolution be human-approved before applying changes.

- Note: Approval notes are not required in practice. `/evolution-approve` silently substitutes `"Approved via command"` when notes are omitted (`based-agent/.pi/extensions/evolution-governor.ts:125`), while the plan calls for approval notes, especially for protected broad-scope artifacts.
- Note: `proposed_content_ref` is accidentally rejected when `proposed_patch` is also present. `promoteCheck` first accepts either resolved content or a patch, but then blocks every proposal with `proposed_patch && !proposed_content`, even if `proposed_content_ref` resolves successfully (`based-agent/.pi/extensions/evolution-governor.ts:93-94`). This is a non-safety functional regression against the documented acceptance of `proposed_content_ref`.
- Note: Rollback of a newly-created target leaves an empty file instead of restoring absence. `snapshotTarget` snapshots missing targets as an empty string (`based-agent/.pi/extensions/evolution-governor.ts:81-86`), and rollback writes that empty snapshot back to the target (`based-agent/.pi/extensions/evolution-governor.ts:154-160`). If promotion creates a new allowlisted prompt/skill/agent file, rollback is not fully reversible.
